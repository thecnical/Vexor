# Requirements Document

## Introduction

Vexor v5 is a major upgrade to the Vexor CLI security toolkit — a Python + Textual TUI application with a FastAPI backend on Render. This document captures 15 new features grouped by priority tier. All features must be fully working implementations (no stubs or fake data). The existing codebase provides: `VexorState` singleton for in-memory state, `BaseScanner` for scan modules, `ToolDetector` for binary detection, `SessionManager` for JSON-based session persistence, SQLAlchemy + aiosqlite already in `requirements.txt`, Playwright in optional deps, and a FastAPI backend with multi-provider AI orchestration.

---

## Glossary

- **Vexor_CLI**: The Python + Textual TUI application running on the user's machine.
- **Vexor_Backend**: The FastAPI service deployed on Render.
- **Scanner**: The vulnerability scanning subsystem (`ScannerScreen` + `BaseScanner` subclasses).
- **Repeater**: The manual HTTP request manipulation screen (`RepeaterScreen`).
- **Intruder**: The automated payload-fuzzing screen (`IntruderScreen`).
- **OSINT_Engine**: The 6-phase intelligence pipeline (`OSINTScreen` + `osint` module).
- **VexorState**: The in-memory singleton that holds scan results, proxy history, and runtime flags.
- **SessionDB**: The SQLite database (via aiosqlite/SQLAlchemy) used for persistent scan storage.
- **ScanSession**: A persisted record of one scan run, including target, timestamp, and all findings.
- **Finding**: A single vulnerability record (`Finding` dataclass in `modules/base.py`).
- **Nuclei**: The open-source vulnerability scanner binary by ProjectDiscovery.
- **SecLists**: The community-maintained security wordlist collection by Daniel Miessler.
- **ExploitDB**: The public exploit database at exploit-db.com, accessible via its API.
- **OOB_Server**: The built-in out-of-band callback server for detecting blind vulnerabilities.
- **Scope_File**: The file at `~/.vexor/scope.txt` that defines allowed scan targets.
- **Workspace**: A per-target directory under `~/.vexor/workspaces/` containing findings, proxy history, and notes.
- **AI_Orchestrator**: The backend component that routes AI requests across multiple providers.
- **PoC**: Proof-of-concept exploit script generated by the AI for a confirmed finding.
- **Playwright**: The browser automation library used for taking screenshots of live hosts.

## Requirements

### Requirement 1: Nuclei Integration

**User Story:** As a penetration tester, I want Vexor to run Nuclei templates against a target, so that I can leverage the community's vulnerability template library alongside Vexor's built-in modules.

#### Acceptance Criteria

1. WHEN the Scanner screen loads, THE Vexor_CLI SHALL detect whether the `nuclei` binary is installed using `ToolDetector` and display its availability status.
2. WHEN `nuclei` is not installed, THE Vexor_CLI SHALL display a message indicating nuclei is unavailable and skip nuclei execution without crashing.
3. WHEN a scan is started and `nuclei` is available, THE Vexor_CLI SHALL execute `nuclei -u <target> -json -silent` as an async subprocess using `run_tool` from `tool_detector.py`.
4. WHEN `nuclei` produces JSON output, THE Vexor_CLI SHALL parse each line as a JSON object and convert it to a `Finding` with severity, module name `"nuclei"`, vulnerability name from the template name, endpoint from the matched URL, and evidence from the matcher output.
5. WHEN nuclei findings are created, THE Vexor_CLI SHALL add them to the Scanner findings table and to `VexorState` using the same path as all other scan modules.
6. WHEN nuclei execution exceeds 120 seconds, THE Vexor_CLI SHALL terminate the subprocess and log a timeout message without crashing.
7. IF the `nuclei` subprocess exits with a non-zero code, THEN THE Vexor_CLI SHALL log the stderr output and continue the scan with findings from other modules.

### Requirement 2: Scan Session Persistence

**User Story:** As a security researcher, I want my scan findings to persist across Vexor restarts, so that I can resume analysis of previous targets without re-running scans.

#### Acceptance Criteria

1. THE Vexor_CLI SHALL initialize a SQLite database at `~/.vexor/vexor.db` on first launch using aiosqlite, creating a `scan_sessions` table and a `findings` table if they do not exist.
2. WHEN a scan completes, THE Vexor_CLI SHALL persist the scan session record (target, timestamp, scan type, module list) and all associated `Finding` objects to `SessionDB` within 2 seconds of scan completion.
3. WHEN Vexor_CLI starts, THE Vexor_CLI SHALL load the 10 most recent `ScanSession` records from `SessionDB` and display them in a "Recent Scans" list on the Scanner screen.
4. WHEN a user selects a past session from the recent scans list, THE Vexor_CLI SHALL load all associated findings into the Scanner findings table and restore the target URL in the scan target input.
5. THE Vexor_CLI SHALL store each `Finding` with all fields: severity, module, vuln, endpoint, param, payload, evidence, description, remediation, ai_note, cve, and the parent session ID.
6. WHEN the user clears the Scanner screen, THE Vexor_CLI SHALL clear the in-memory display only and SHALL NOT delete persisted session data from `SessionDB`.
7. IF `SessionDB` is unavailable or corrupted, THEN THE Vexor_CLI SHALL log the error, disable persistence silently, and continue operating in memory-only mode.

### Requirement 3: Repeater → Send to Scanner

**User Story:** As a penetration tester, I want to send a request from the Repeater directly to the Scanner, so that I can run all vulnerability modules against a specific endpoint I have already crafted.

#### Acceptance Criteria

1. THE Vexor_CLI SHALL display a "Send to Scanner" button in the Repeater screen's button row.
2. WHEN the user clicks "Send to Scanner" and the Repeater URL input is empty, THE Vexor_CLI SHALL display an error notification and take no further action.
3. WHEN the user clicks "Send to Scanner" with a valid URL, THE Vexor_CLI SHALL extract the URL from the Repeater URL input, set it as the scan target in `VexorState`, navigate to the Scanner screen, and pre-populate the Scanner target input with that URL.
4. WHEN the Scanner screen receives a pre-populated target via "Send to Scanner", THE Vexor_CLI SHALL automatically start a full scan against that target without requiring additional user input.
5. WHEN the Repeater has a raw HTTP request in the request textarea, THE Vexor_CLI SHALL parse the `Host` header from the raw request and use it to construct the full target URL if the Repeater URL input is empty.

### Requirement 4: Intruder — SecLists Payload Import

**User Story:** As a penetration tester, I want to import SecLists wordlists directly into the Intruder, so that I can use community-curated payloads for fuzzing attacks.

#### Acceptance Criteria

1. THE Vexor_CLI SHALL display a "SecLists" button in the Intruder screen's payload section.
2. WHEN the user clicks "SecLists", THE Vexor_CLI SHALL display a selection menu listing at minimum these categories: `Passwords/Common-Credentials`, `Fuzzing/SQLi`, `Fuzzing/XSS`, `Discovery/Web-Content/common`, `Fuzzing/LFI`, `Fuzzing/SSTI`.
3. WHEN the user selects a SecLists category, THE Vexor_CLI SHALL check whether the corresponding wordlist file exists under `~/.vexor/seclists/`.
4. WHEN the wordlist file does not exist, THE Vexor_CLI SHALL download it from the official SecLists GitHub raw URL (`https://raw.githubusercontent.com/danielmiessler/SecLists/master/<path>`) using `httpx` and save it to `~/.vexor/seclists/<category>/`.
5. WHEN the download completes, THE Vexor_CLI SHALL load the wordlist lines into the Intruder payload textarea, replacing existing content, and notify the user of the count loaded.
6. WHEN the wordlist file already exists locally, THE Vexor_CLI SHALL load it directly without re-downloading.
7. IF the download fails due to a network error, THEN THE Vexor_CLI SHALL display an error notification with the failure reason and leave the payload textarea unchanged.
8. WHEN loading a wordlist, THE Vexor_CLI SHALL skip blank lines and lines starting with `#` and load a maximum of 10,000 lines to prevent memory issues.

### Requirement 5: CVE-to-Exploit Mapping

**User Story:** As a penetration tester, I want Vexor to automatically search ExploitDB when a CVE is found, so that I can immediately know whether a public exploit exists for the vulnerability.

#### Acceptance Criteria

1. WHEN a `Finding` with a non-empty `cve` field is added to `VexorState`, THE Vexor_CLI SHALL automatically trigger an ExploitDB search for that CVE ID.
2. THE Vexor_CLI SHALL query the ExploitDB search API at `https://www.exploit-db.com/search?cve=<CVE-ID>&type=exploits` using an HTTP GET request with a browser-like User-Agent header.
3. WHEN the ExploitDB response contains one or more exploit entries, THE Vexor_CLI SHALL update the corresponding `Finding`'s `ai_note` field with the exploit title, EDB-ID, and direct URL.
4. WHEN the ExploitDB response contains no exploit entries, THE Vexor_CLI SHALL set the `Finding`'s `ai_note` to `"No public exploit found on ExploitDB"`.
5. WHEN the Scanner detail panel displays a finding with an ExploitDB result, THE Vexor_CLI SHALL render the exploit information in the detail panel below the CVE field.
6. IF the ExploitDB API request fails or times out after 10 seconds, THEN THE Vexor_CLI SHALL log the failure and leave the `ai_note` unchanged without blocking the UI.

### Requirement 6: Scope Management

**User Story:** As a penetration tester, I want to define a scope file so that all Vexor modules only test targets within the authorized scope.

#### Acceptance Criteria

1. THE Vexor_CLI SHALL read scope rules from `~/.vexor/scope.txt` at startup, where each non-blank, non-comment line is a scope entry (domain, IP, or CIDR range).
2. THE Vexor_CLI SHALL expose a `ScopeManager` class with an `in_scope(url_or_ip: str) -> bool` method that returns `True` if the target matches any scope entry.
3. WHEN `~/.vexor/scope.txt` does not exist or is empty, THE `ScopeManager` SHALL treat all targets as in-scope (permissive default).
4. WHEN a scan module attempts to send a request to a URL, THE Vexor_CLI SHALL call `ScopeManager.in_scope()` before sending and skip the request if the result is `False`.
5. WHEN a target is out of scope, THE Vexor_CLI SHALL log a `[SCOPE] Skipped: <url>` message to the scan log without adding a finding.
6. THE Vexor_CLI SHALL display the current scope entry count in the Config screen.
7. THE Vexor_CLI SHALL provide a "Edit Scope" button in the Config screen that opens `~/.vexor/scope.txt` for editing using the system's default text editor via `subprocess`.

### Requirement 7: Blind XSS/SSRF Callback Server

**User Story:** As a penetration tester, I want a built-in out-of-band callback server, so that I can detect blind XSS and blind SSRF vulnerabilities that do not produce visible responses.

#### Acceptance Criteria

1. THE Vexor_CLI SHALL include a built-in `OOB_Server` that listens on a configurable local port (default `7331`) for HTTP callbacks.
2. WHEN the user starts the `OOB_Server`, THE Vexor_CLI SHALL bind an asyncio HTTP server to `0.0.0.0:<port>` and generate a unique session token used as a path prefix for all callback URLs.
3. WHEN the `OOB_Server` receives an HTTP request on any path containing the session token, THE Vexor_CLI SHALL record the callback with timestamp, source IP, HTTP method, path, and any query parameters.
4. WHEN a callback is recorded, THE Vexor_CLI SHALL create a `Finding` with severity `HIGH`, module `"oob_server"`, vuln name derived from the path prefix (e.g., `"Blind XSS Callback"` or `"Blind SSRF Callback"`), and add it to `VexorState`.
5. THE Vexor_CLI SHALL display a dedicated "OOB Callbacks" panel in the Scanner screen showing all received callbacks in real time.
6. WHEN the `OOB_Server` is running, THE Vexor_CLI SHALL provide callback URL templates for blind XSS (`<script src="http://<local-ip>:<port>/<token>/xss"></script>`) and blind SSRF (`http://<local-ip>:<port>/<token>/ssrf`) that the user can copy.
7. WHEN the user stops the `OOB_Server`, THE Vexor_CLI SHALL cleanly shut down the asyncio server and release the port.
8. IF the configured port is already in use, THEN THE Vexor_CLI SHALL automatically try the next available port up to `port + 10` and notify the user of the actual port used.

### Requirement 8: Screenshot Module

**User Story:** As a security researcher, I want Vexor to automatically take screenshots of live hosts discovered during OSINT, so that I can visually verify targets without opening a browser.

#### Acceptance Criteria

1. WHEN the OSINT_Engine completes Phase 2 (live host check) and Playwright is installed, THE Vexor_CLI SHALL offer a "Screenshot Live Hosts" button in the OSINT screen.
2. WHEN the user clicks "Screenshot Live Hosts", THE Vexor_CLI SHALL launch a headless Chromium browser via `playwright.async_api` and navigate to each live host URL.
3. WHEN Playwright is not installed, THE Vexor_CLI SHALL display a message `"Playwright not installed — run: pip install playwright && playwright install chromium"` and disable the screenshot button.
4. WHEN a screenshot is taken, THE Vexor_CLI SHALL save it as a PNG file to `~/.vexor/screenshots/<domain>_<timestamp>.png`.
5. WHEN a screenshot is saved, THE Vexor_CLI SHALL add an `INFO` finding to the OSINT results table with the vuln name `"Screenshot Captured"` and the file path as evidence.
6. WHEN navigating to a live host for a screenshot, THE Vexor_CLI SHALL set a page timeout of 15 seconds and skip the host if the timeout is exceeded.
7. IF Playwright fails to take a screenshot for a specific host, THEN THE Vexor_CLI SHALL log the error and continue with the remaining hosts.
8. THE Vexor_CLI SHALL process screenshot tasks concurrently with a maximum of 3 simultaneous browser pages to limit resource usage.

### Requirement 9: Report Templates

**User Story:** As a security consultant, I want multiple report format templates, so that I can deliver findings in the format expected by different clients and bug bounty platforms.

#### Acceptance Criteria

1. THE Vexor_CLI SHALL support four report templates: `executive`, `technical`, `hackerone`, and `bugcrowd`.
2. WHEN generating an `executive` report, THE Vexor_CLI SHALL produce an HTML document containing: an executive summary paragraph, a risk score (0–100) calculated from finding severities, a findings-by-severity bar chart rendered as ASCII/HTML, and top-3 recommended remediations.
3. WHEN generating a `technical` report, THE Vexor_CLI SHALL produce an HTML document containing: all findings with full evidence, payloads, remediation steps, and CVE references.
4. WHEN generating a `hackerone` report, THE Vexor_CLI SHALL produce a Markdown document following HackerOne's report structure: Title, Severity, Summary, Steps to Reproduce, Impact, and Supporting Material sections.
5. WHEN generating a `bugcrowd` report, THE Vexor_CLI SHALL produce a Markdown document following Bugcrowd's VRT format: Title, Vulnerability Type, Severity, Description, Steps to Reproduce, and Proof of Concept sections.
6. THE Vexor_CLI SHALL display a template selector dropdown in the Reports screen with all four options.
7. WHEN a report is generated, THE Vexor_CLI SHALL save it to `~/.vexor/reports/<template>_<target>_<timestamp>.<ext>` and display the full path in the Reports screen.
8. WHEN the AI Enhance button is clicked on a generated report, THE Vexor_CLI SHALL send the findings summary to the `AI_Orchestrator` and insert the AI-generated narrative into the report's summary section.

### Requirement 10: Workspace/Project System

**User Story:** As a penetration tester managing multiple engagements, I want each target to have its own workspace, so that findings, proxy history, and notes are organized per target.

#### Acceptance Criteria

1. THE Vexor_CLI SHALL create a workspace directory at `~/.vexor/workspaces/<sanitized-target>/` when a new target is set.
2. WHEN a workspace is created, THE Vexor_CLI SHALL initialize it with subdirectories: `findings/`, `proxy/`, `notes/`, and `screenshots/`.
3. THE Vexor_CLI SHALL display a workspace selector in the Dashboard screen listing all existing workspaces with their target name, creation date, and finding count.
4. WHEN the user selects a workspace, THE Vexor_CLI SHALL load the workspace's findings into `VexorState`, set the scan target, and switch to the Scanner screen.
5. WHEN a scan completes, THE Vexor_CLI SHALL save findings to the active workspace's `findings/` directory as a JSON file named `<timestamp>_<scan_type>.json`.
6. WHEN proxy traffic is captured, THE Vexor_CLI SHALL save proxy entries to the active workspace's `proxy/` directory.
7. WHEN no workspace is active, THE Vexor_CLI SHALL use a default workspace named `default` and create it if it does not exist.

### Requirement 11: Notes Panel

**User Story:** As a penetration tester, I want a notes panel within Vexor, so that I can record observations and findings context without switching to an external editor.

#### Acceptance Criteria

1. THE Vexor_CLI SHALL add a "Notes" entry to the sidebar navigation and a corresponding `NotesScreen` widget.
2. THE `NotesScreen` SHALL contain a full-screen `TextArea` widget for free-form text entry.
3. WHEN the user types in the notes `TextArea`, THE Vexor_CLI SHALL auto-save the content to `~/.vexor/sessions/notes_<active-workspace>.txt` after a 2-second debounce delay.
4. WHEN the `NotesScreen` is opened, THE Vexor_CLI SHALL load the notes file for the active workspace if it exists.
5. WHEN no active workspace notes file exists, THE Vexor_CLI SHALL start with an empty `TextArea`.
6. THE `NotesScreen` SHALL display a "Save" button that immediately writes the current content to disk and shows a confirmation notification.
7. THE `NotesScreen` SHALL display a "Clear" button that clears the `TextArea` content and deletes the notes file after user confirmation.

### Requirement 12: AI Chat History

**User Story:** As a security analyst, I want the AI panel to maintain conversation context across messages, so that I can have a multi-turn dialogue about findings without repeating context.

#### Acceptance Criteria

1. THE Vexor_CLI SHALL maintain a conversation history list in the `AIScreen` widget, storing each message as a dict with `role` (`"user"` or `"assistant"`) and `content` fields.
2. WHEN the user submits a message in the AI panel, THE Vexor_CLI SHALL append the user message to the conversation history before sending to the `AI_Orchestrator`.
3. WHEN sending a request to the `AI_Orchestrator`, THE Vexor_CLI SHALL include the last 10 messages from conversation history as context.
4. WHEN the `AI_Orchestrator` returns a response, THE Vexor_CLI SHALL append the assistant response to the conversation history.
5. THE `AIScreen` SHALL display the full conversation history in a scrollable log, with user messages in cyan and assistant messages in magenta.
6. THE `AIScreen` SHALL display a "Clear History" button that resets the conversation history list and clears the display log.
7. WHEN the conversation history exceeds 50 messages, THE Vexor_CLI SHALL trim the oldest messages to keep only the most recent 50, preserving the last system context message if present.

### Requirement 13: Vexor Cloud Sync

**User Story:** As a security professional, I want to sync my findings to the Vexor backend, so that I can view and manage them from the web dashboard.

#### Acceptance Criteria

1. THE Vexor_CLI SHALL provide a "Sync to Cloud" button in the Reports screen and the Dashboard screen.
2. WHEN the user clicks "Sync to Cloud" and is not authenticated, THE Vexor_CLI SHALL display a notification directing the user to run `vexor auth login` and take no further action.
3. WHEN the user clicks "Sync to Cloud" and is authenticated, THE Vexor_CLI SHALL POST the current session's findings as a JSON payload to `<BACKEND_URL>/api/v1/sync/findings` with the auth token in the `Authorization: Bearer <token>` header.
4. WHEN the backend returns HTTP 200, THE Vexor_CLI SHALL display a success notification with the count of synced findings.
5. WHEN the backend returns a non-200 response, THE Vexor_CLI SHALL display an error notification with the HTTP status code and response message.
6. THE Vexor_Backend SHALL expose a `POST /api/v1/sync/findings` endpoint that accepts a JSON array of findings, associates them with the authenticated user, and stores them in the backend database.
7. IF the sync request times out after 30 seconds, THEN THE Vexor_CLI SHALL display a timeout error notification and log the failure.

### Requirement 14: Team Collaboration

**User Story:** As a team lead, I want multiple team members to work on the same target simultaneously, so that we can share findings and coordinate during a penetration test.

#### Acceptance Criteria

1. THE Vexor_Backend SHALL expose a WebSocket endpoint at `/api/v1/collab/<session-id>` that accepts authenticated connections.
2. WHEN a Vexor_CLI instance connects to a collaboration session, THE Vexor_Backend SHALL broadcast all subsequent finding additions to all other connected clients in that session.
3. WHEN a remote finding is received via WebSocket, THE Vexor_CLI SHALL add it to `VexorState` and update the Scanner findings table with a `[REMOTE]` prefix on the module name.
4. THE Vexor_CLI SHALL display a "Join Session" button in the Dashboard screen that accepts a session ID and connects to the collaboration WebSocket.
5. WHEN the WebSocket connection is established, THE Vexor_CLI SHALL display the count of connected collaborators in the status bar.
6. WHEN the WebSocket connection is lost, THE Vexor_CLI SHALL attempt to reconnect up to 3 times with a 5-second delay between attempts before displaying a disconnection notification.
7. THE Vexor_Backend SHALL authenticate WebSocket connections using the same JWT token used for REST API calls, rejecting unauthenticated connections with a `4001` close code.

### Requirement 15: AI-Generated PoC

**User Story:** As a penetration tester, I want the AI to generate a working proof-of-concept exploit script for confirmed findings, so that I can demonstrate impact to clients without writing exploits from scratch.

#### Acceptance Criteria

1. THE Vexor_CLI SHALL display a "Generate PoC" button in the Scanner detail panel when a finding with severity `HIGH` or `CRITICAL` is selected.
2. WHEN the user clicks "Generate PoC", THE Vexor_CLI SHALL send a structured prompt to the `AI_Orchestrator` containing the finding's vuln type, endpoint, param, payload, evidence, and CVE (if present).
3. WHEN the `AI_Orchestrator` returns a PoC script, THE Vexor_CLI SHALL display it in a new panel below the finding detail with syntax highlighting using Rich markup.
4. WHEN a PoC is generated, THE Vexor_CLI SHALL save it to `~/.vexor/reports/poc_<vuln-slug>_<timestamp>.py` (or `.sh` for shell-based exploits).
5. THE AI prompt for PoC generation SHALL instruct the `AI_Orchestrator` to produce a self-contained Python or shell script that demonstrates the vulnerability, includes comments explaining each step, and includes a disclaimer that it is for authorized testing only.
6. WHEN the `AI_Orchestrator` is unavailable or returns an empty response, THE Vexor_CLI SHALL display a notification directing the user to authenticate with `vexor auth login`.
7. IF the finding's vuln type is not exploitable via a script (e.g., informational headers), THEN THE Vexor_CLI SHALL display a message `"PoC not applicable for this finding type"` instead of calling the AI.
